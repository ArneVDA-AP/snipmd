## Start-time probe: what WebView2 costs on this PC

To learn which levers can reach the 300 ms budget, I built a minimal Tauri app with the same versions (tauri 2.12.4,
wry 0.57.0, webview2-com 0.39.1, same release profile) that logs each step of its start. Sources and raw data:
`findings/windows/probe/` (to build it: copy `src-tauri/icons/icon.ico` to `icons/`, `dist/assets/*` to
`dist/snip/`, and `src-tauri/Cargo.lock`, then `cargo build --release`). Each variant: 1 warm-up start, then 8
starts, round-robin across variants. Medians in ms from launch:

| Variant | main | setup | webview built | first script (`head`) | SnipMD bundle run | painted |
|---|---|---|---|---|---|---|
| A plain window, empty page | 8.4 | 15.9 | 644.0 | 668.8 | | 684.4 |
| B SnipMD window (frameless + transparent) | 8.4 | 16.0 | 648.1 | 673.4 | | 680.6 |
| C B + lean browser args (1) | 8.6 | 16.2 | 638.9 | 666.4 | | 676.8 |
| D B + `--disable-gpu` (diagnostic) | 8.6 | 16.2 | 636.8 | 662.2 | | 669.5 |
| E B + SnipMD's real bundle | 8.1 | 16.2 | 644.3 | 670.2 | 698.8 | 706.2 |

(1) `--disable-features=msWebOOUI,msPdfOOUI,msSmartScreenProtection,Translate,OptimizationHints,MediaRouter,AutofillServerCommunication --disable-background-networking --disable-component-update --disable-extensions --disable-sync --no-first-run --disable-default-apps`

Resident variant (window created hidden at first start; a second launch goes through
`tauri-plugin-single-instance` and the first process shows the window), 8 trials:

| Measure | Value |
|---|---|
| Second launch to window shown and painted (median) | 51 ms (range 47.6 to 56.6) |
| Second process exits after launch | 46.5 to 51.7 ms |
| Idle hidden cost, empty page: processes / private working set / private bytes | 7 / 83.8 MB / 160.9 MB |

What this shows (observed unless marked):
- `WebviewWindowBuilder::build()` takes about 620 to 630 ms on this PC for an empty page. That is WebView2
  environment and controller creation, before any page loads. A cold start cannot reach 300 ms here, whatever
  SnipMD does.
- Window style, browser arguments and the GPU change the start by less than 10 ms. Lean browser args are not a
  start-time lever (still useful to turn autofill off).
- SnipMD's bundle adds about 30 ms over an empty page (`head` 670 to bundle run 699). A smaller bundle saves at most
  that.
- Keeping a hidden instance running brings a later double-click to about 50 ms. The cost is the idle memory
  (about 84 MB private working set for an empty page; SnipMD with its notes would be more, inferred) and a start
  at login or "hide instead of quit" on close. This is the only lever found that meets the budget.
- Inferred, not tested: the CI runner's 462 ms vs 620 ms here may come from Defender scanning
  `msedgewebview2.exe` children or from two monitors; I did not change security settings to test it.

## Probe 2: a broker that keeps the WebView2 browser process alive (idea 4)

Question: WebView2 hosts that use the same user data folder and the same environment options share one browser
process. Does a hidden broker that only keeps that browser process alive make a separate, cold start faster?
Setup: the probe with `PROBE_HOLD=1` is the broker (hidden window, empty page, never exits). The measured starts are
separate processes (no single-instance hand-off), frameless + transparent, default browser args, same user data
folder. Phase 1 without broker, phase 2 with broker, phase 3 without broker again (drift check); each phase 1
warm-up + 8 starts per page, round-robin. Script `findings/windows/probe/run-shared.ps1`, raw data
`shared-20261021.csv`. Medians in ms from launch:

| Phase | Page | webview built | first script (`head`) | SnipMD bundle run | painted (min to max) |
|---|---|---|---|---|---|
| 1 no broker | empty | 605.4 | 622.2 | | 674.8 (657.2 to 723.9) |
| 1 no broker | SnipMD bundle | 602.2 | 620.6 | 647.8 | 712.0 (662.3 to 776.1) |
| 2 with broker | empty | 165.6 | 181.0 | | 189.1 (177.6 to 203.3) |
| 2 with broker | SnipMD bundle | 161.2 | 177.3 | 206.0 | 210.6 (206.4 to 229.5) |
| 3 no broker again | empty | 597.0 | 613.0 | | 658.0 (631.2 to 720.1) |
| 3 no broker again | SnipMD bundle | 594.5 | 609.6 | 642.6 | 707.4 (631.6 to 730.4) |

| Broker cost (idle, hidden, empty page) | Value |
|---|---|
| WebView2 processes | 6 |
| Private working set, broker host + its WebView2 processes | 76.1 MB |
| Broker processes still alive after phase 2 | 6 of 6 |

What this shows:
- Observed: with the broker running, webview creation drops from about 600 ms to about 163 ms, and the SnipMD bundle
  has run at 206 ms instead of 645 ms. Phases 1 and 3 agree, so this is not drift.
- Inferred: SnipMD's `ready` comes about 60 ms after `script` (measure.ps1), so a real SnipMD start with a broker
  would be ready at about 265 to 290 ms, just under the 300 ms budget, with little margin.
- Compared with the resident SnipMD (51 ms, 84 MB): the broker is slower (about 270 ms) and costs about the same idle
  memory (76 MB). Its gains are elsewhere: SnipMD keeps a normal life cycle (it really quits on close, no hidden
  window with notes in memory), and the broker can be started only when it is likely needed (at login, or when an
  image lands on the clipboard).
- Conditions (inferred from the WebView2 model, not tested here): SnipMD and the broker must use the same user data
  folder and identical environment options (browser args, language); otherwise WebView2 starts a second browser
  process or refuses the environment.
- The open points of this probe are tested in Probe 3.

## Proposal: start budget (owner asked to put this in the report)

This is the tester's recommendation for the dev session, not a measured result. Facts it rests on are in the probe
sections above; the rest is marked inferred.

**Recommendation: keep SnipMD warm, as a setting; no broker. Split the SPEC §9 start budget into cold and warm.**

| Budget | Proposed target | Measured now on this PC |
|---|---|---|
| Cold start, double-click to typing (from launch) | < 800 ms | 722 to 784 ms (main e951acb) |
| Warm start, double-click to typing (from launch) | < 150 ms | 51 ms window shown (probe, resident); SnipMD itself not measured |

Why not a broker:
- Windows only. Sharing a browser process between host processes is a WebView2 feature. On macOS Tauri uses
  WKWebView, whose web processes belong to one app; Linux (WebKitGTK) is the same (inferred). A broker does not widen
  OS support.
- Fragile: a start with options that differ from the broker's fails (Probe 3, 6 of 6, HRESULT 0x8007139F). Every
  SnipMD or WebView2 runtime update would have to keep the broker and the app in step. The runtime-update case is not
  tested.
- Only just within budget: 314 to 343 ms from launch (Probe 3).
- Dominated by keeping SnipMD warm: about the same idle memory (broker 71 to 76 MB, resident probe 84 MB) for a
  start that is about six times slower.

Proposed design, "warm shell, cold content" (inferred, not measured):
- On close, SnipMD hides its window, saves the session and empties the editor, so no note text stays in memory.
- On the next double-click (single-instance hand-off), WebView2 and the bundle are already loaded; only the session
  is read and rendered, which took about 60 to 70 ms after `script` in measure.ps1. Estimate: about 100 ms.
- A setting "Keep SnipMD ready in the background", on by default and easy to turn off; "Start at sign-in" as a
  separate, opt-in choice. With the setting off, the cold budget applies.
- The installer and updater must close the hidden instance before replacing files.
- Idle cost to measure once built: memory of the hidden SnipMD with an empty editor (probe baseline 84 MB).

What other apps do (from general knowledge, not checked in this session):
- Electron apps (VS Code, Obsidian, Slack, Discord, Notion) start in roughly 1 to 3 s; Slack, Discord and Teams
  start at sign-in and hide on close.
- Microsoft's WebView2 apps (new Teams, new Outlook) often keep running in the background; Edge's "Startup boost" is
  the broker idea for Edge itself.
- The apps that start cold in well under 300 ms are native (Notepad and Snipping Tool on Windows 11, Sublime Text,
  Zed). No webview app known to the tester starts cold under 300 ms on Windows.

macOS: WKWebView likely starts faster than WebView2 (inferred). The probe in `findings/windows/probe/` can be
ported to measure it on a Mac (main now has `tools/measure/macos-probe.sh`).
